# 3DStockTheme: the technical reference

An on-console theme installer for the HOME Menu's own theme system, in three folders:

- `core/`: plain C that turns theme zips into the pieces of the theme DLC pack that [`tools/theme-pack/`](../tools/theme-pack/) builds on the Mac (content 0 with the catalogue, one content per theme, the TMD, the ticket, and the delta that adds themes to an installed pack), and since 0.9.3 the HOME Menu's badge collection as the Mac tool `tools/badges/badge_sets.py` handles it (`core/badge.c`, `badge_png.c`, `badge_set.c`). It compiles on the Mac and for the 3DS.
- `app/`: **3DStockTheme**, the 3DS application on top of it (section "3DStockTheme" below): an interface after the approved prototype that installs a theme into the pack through AM (since 1.0.0-beta.2 the first theme creates the pack on a console that has none), from a file chosen in a folder view of the SD card or from a QR code whose address it downloads, with or without the theme's music; for a theme that is installed already it deletes that theme from the pack (as the HOME Menu's own Delete does) or the file on the card. A theme can be a theme zip or a "theme installer" CIA that carries one. Since 0.9.3 it also appends a badge set (a folder or a zip of PNG files, or one PNG, from the SD card or by QR code) to the HOME Menu's badge collection and removes the last set it appended (section "Badges (0.9.3)").
- `uikit/`: the UI kit the application's interface is drawn with: the drawing layer, the looks, the building blocks of the screens and the sound (the interface sounds and the music through `ndsp`), on citro2d, citro3d and libctru. It includes nothing of the application (`host/test_kit_bounds.py` checks that), its art generator `uikit/art/art.py` runs without the application too (`host/test_art_alone.py`), which brings its own images through the generator's one hook (`--app`), and it is a library of its own, "3ds-uikit" (version 0.1.0 in `uikit/VERSION`, the zlib licence in `uikit/LICENSE`), with its own `uikit/Makefile`, which the Makefile here calls for the kit's tests, its example and its docs' pictures; see [`uikit/README.md`](../uikit/README.md). It is a repository of its own, "3ds-uikit", taken here as a git submodule at `uikit/` pinned to one commit of it (`.gitmodules` at the repository's root names it by the relative URL `../3ds-uikit`, beside this repository): clone with `git clone --recurse-submodules`, or run `git submodule update --init` in a clone or a new worktree before building; with the repositories as folders on one disk git wants `-c protocol.file.allow=always` on both. The pinned commit is what `git submodule status` shows (`git ls-tree HEAD uikit` here); the pin moves with `git -C uikit checkout <commit of the kit>` and a commit of `uikit` here, and a change to the kit's files is a commit in the kit's repository first.

## What it does

- Reads a theme zip in the Anemone / Theme Plaza format from a byte source the caller provides: `body_LZ.bin`, optional `bgm.bcstm`, `info.smdh` at the zip root, other members ignored. Name, description and the large icon come from `info.smdh` exactly as `theme_pack.py` reads them (title slot 0 first, then the first filled slot, then the zip name; Python's UTF-16 decoding with replacement and `strip()`); the tests compare the core's result with `theme_pack.read_theme` on the fixtures and on SMDH edge cases. The use-BGM byte (0x5 of the decompressed body) is reported, and a mismatch with `bgm.bcstm` is a warning, never an error.
- Writes through sinks the caller provides (a file on the Mac, an AM content handle on the console): content 0, every theme content (each an NCCH CFA), the TMD with its hash chain, a ticket with rights for indices 0 to 0x3FF, and for a delta the new TMD.
- One title only: `TP_TITLE_ID`, `0004008C00009809` (EUR theme DLC, the spare variation 09; official themes use 00 to 04). Every call that takes a title ID and every installed TMD must carry it, anything else is `TP_E_TITLE`, so the application cannot import into an official theme title by mistake. The Mac builder keeps its `--variation`; this core has no such choice.
- Keeps the rules of `theme_pack.py`: content indices 1 to 349; the next index is one above the larger of the caller's mark (the highest index ever handed out) and the highest index in use (the installed TMD's), so an index is never handed out twice, also not after a reinstall that dropped a theme; a delta keeps every installed content record as installed, content 0 gets ID `0x10000` + the new title version, the version goes up by one, only content 0 and the new themes are imported, no ticket.
- Reads a "theme installer" CIA (`core/cia.c`), the second kind of theme file some sites offer: an unencrypted CIA whose content 0 is an NCCH with a RomFS holding `config.ini` (`location=theme.zip`, `destination=Themes/<name>.zip`) and the theme zip that `location` names. The core hands that zip on as a window into the CIA, so the zip reader above reads it in place. Which kind a file is comes from its first bytes (`tp_kind`), never from its name; the core never installs such a CIA, it only takes the zip out.
- Reads back what is installed, from bytes the application fetches: the catalogue of an installed content 0 (`ContentInfoArchive_EUR_<lang>.bin` and `icons/<index>.icn`) per index with name, description, enabled flag and icon, and the highest index; and whether a stored TMD is still what AM reports (title version; per content index, content ID and size), or the first record that differs.
- The HOME Menu's badge collection (0.9.3, `core/badge.h`): the sets of the decrypted `BadgeData.dat` and `BadgeMngFile.dat` listed, one set (PNG files, read by `core/badge_png.c`) appended without changing anything that exists, the last set removed back to its earlier bytes, every placement of the saved layouts checked against the badges, all the same byte for byte as `tools/badges/badge_sets.py` does it; buffers in and out, as the theme core.
- For the preview (0.9.2): an open theme's decoded body and its `bgm.bcstm` (`core/media.c`), the wallpapers a decoded body describes (`core/body.c`, after 3dbrew "Home Menu/Themes") and a BCSTM stream decoded to PCM (`uikit/source/bcstm.c`, after 3dbrew "BCSTM"); both decoders read hostile bytes and refuse what does not fit the file. For measuring only, `tp_set_phase` tells a caller when the core's work on a theme changes its kind (unzip with its CRC-32, the LZ11 check of the body, the RomFS block hashes); the core reads no clock.

## API (`core/tp.h`)

```c
typedef struct { void *ctx; uint64_t size; int (*read)(void *ctx, uint64_t offset, void *buf, size_t len); } tp_source;
typedef struct { void *ctx; int (*write)(void *ctx, const void *buf, size_t len); } tp_sink;   /* in order, <= 16 KiB */

int tp_theme_open(tp_theme *t, const tp_source *zip, const char *fallback_name);  /* checks and hashes; name, icon, flags */
int tp_theme_peek(tp_theme *t, const tp_source *zip, const char *fallback_name);  /* only directory and SMDH: for a list */
int tp_theme_drop_bgm(tp_theme *t);           /* an open theme without bgm.bcstm, its body's use-BGM byte cleared */
int tp_kind(const tp_source *src);                                                  /* TP_KIND_ZIP, _CIA or _NONE by content */
int tp_cia_open(const tp_source *cia, int verify, tp_package *p);                   /* the zip in a theme installer CIA */
int tp_theme_in(const tp_source *file, int verify, tp_package *p, const tp_source **zip, int *kind);  /* either kind */
int tp_theme_content(const tp_theme *t, uint64_t title_id, uint16_t index, const tp_sink *out /* NULL: measure */, tp_content *record);
int tp_catalogue_content(const tp_catalogue *c, uint64_t title_id, uint32_t content_id, const tp_sink *out, tp_content *record);
int tp_tmd(uint64_t title_id, uint16_t version, const tp_content *records, size_t count, const tp_sink *out);
int tp_ticket(uint64_t title_id, uint64_t ticket_id, const uint8_t title_key[16], const tp_sink *out);
int tp_next_index(const uint16_t *used, size_t count, uint16_t top, uint16_t *index);              /* 1 + max(top, used) */
int tp_delta_plan(const uint8_t *installed_tmd, size_t size, uint64_t title_id, const tp_catalogue *c, tp_delta *plan);
int tp_delta_tmd(const uint8_t *installed_tmd, size_t size, const tp_delta *plan, const tp_content *content0, const tp_content *added, const tp_sink *out);
int tp_installed_top(const tp_source *archive, uint16_t *top);                                       /* installed content 0 */
int tp_installed_entry(const tp_source *archive, const tp_source *icon, uint16_t index, tp_installed *entry);
int tp_tmd_check(const uint8_t *tmd, size_t size, uint16_t version, const tp_am_content *am, size_t count, tp_difference *difference);
void tp_set_phase(void (*tell)(void *ctx, int phase), void *ctx);                     /* TP_PHASE_*, for measuring */
```

The preview's parts have headers of their own: `core/media.h` (`tp_theme_body`, `tp_theme_bgm`, `tp_body_decode`), `core/body.h` (`tp_body_read`, `tp_wall_x`, `tp_wall_texel`), `uikit/include/bcstm.h` (`bcstm_open`, `bcstm_read`, `bcstm_rewind`).

Every `title_id` argument must be `TP_TITLE_ID`.

A catalogue (`tp_catalogue`) is the list of themes the pack holds (index, name, description), `top` (the highest index ever handed out; indices up to it without a theme are listed as "(removed)" with a grey icon) and an icon callback, so 349 icons need not be in memory at once.

AM needs the TMD before the contents, so every content call runs twice: with `out == NULL` it measures (size and SHA-256 for the TMD record), with a sink it writes and the record comes out again.

- First install: `tp_theme_open` each zip; measure content 0 (ID 0) and each theme (ID = index); `tp_ticket`; `tp_tmd` (version 0); write content 0 and the themes.
- Adding themes: `tp_tmd_check` of the stored TMD against AM's list (`TP_E_STALE`: read the installed state again first); `tp_delta_plan` on that TMD and the new catalogue (refuses with `TP_E_GONE` if an installed theme is missing from it, `TP_E_NOTHING`, `TP_E_VERSION`, `TP_E_ID`); measure content 0 with `plan.content0_id` and the themes in `plan.add`; `tp_delta_tmd`; write content 0 and those themes.
- After an error a sink may hold part of a content: cancel that import. Results are `tp_result` values; `tp_result_name` and `tp_result_text` name them.

What the application has to keep, because the core only computes: the TMD it imported last (the delta starts from it byte for byte; AM's content list, as `tools/theme-pack/import-test` reads it, gives index, content ID, size and flags but no hash, so `tp_tmd_check` can tell whether the stored TMD is still the installed one, while the hashes come only from the stored TMD), and its mark (the highest index ever handed out). Names, descriptions and icons of installed themes, also of themes deleted in HOME (their TMD records and catalogue entries stay), can be read back from the installed content 0 with `tp_installed_entry` instead of trusting the application's own store.

## What it writes, and how it differs from the pack that passed on the console

The formats are those of `theme_pack.py` and its README ("What the pack contains, and why"); the NCCH, RomFS, ExeFS, TMD and ticket layouts follow makerom at tag `makerom-v0.19.0` (commit `e8f5f529`, `romfs_gen.c`, `ncch.c`, `exefs.c`, `tmd.c`, `tik.c`, `cia.c`) and the bytes of `theme-pack-rebuild-3-themes.cia`, the makerom-built pack installed on 2026-11-12. NCCH: CFA, flags `00 00 00 00 01 01 00 05` (platform CTR, simple content, no crypto), product code `CTR-N-THMP`, maker `00`, partition and program ID = title ID; ExeFS only in content 0 (the "Custom themes" SMDH); RomFS at a 0x1000 boundary, IVFC with 0x1000 blocks, level 3 after the master hash, then levels 1 and 2; TMD and ticket as makerom writes them with the two changes `theme_pack.py` patches in (real content indices, rights 0 to 0x3FF).

Differences from that pack (each one is untested on a console until the next console test):

| Difference | Why | Risk |
| --- | --- | --- |
| NCCH header, TMD and ticket signatures are 0x100 bytes of 0xFF; makerom signs with its test key | no key in this code; makerom itself writes 0xFF when it cannot sign | Low. Neither is valid on a retail console; Luma3DS v13.5 `patchSignatureChecks` (arm9 `patches.c`) makes Process9's check return success without reading the bytes (verified in source). Not seen on a console: an install with 0xFF signatures. A delta TMD keeps the installed TMD's signature, as `theme_pack.py delta` does. |
| Content 0's RomFS lists its files in a fixed order (`MetaDataContentHeader.bin`, the archives en, es, fr, de, it, nl, pt, ru, then `icons/1.icn` up); makerom used the Mac's directory listing order | reproducible on any platform | Low. The files and their bytes are the same (compared after extraction with ctrtool), the hash tables index the same names, sizes are equal; HOME opens the files by path. Content 0's SHA-256 differs. |
| Ticket ID and title key come from the caller; makerom takes random ones (`tpack` derives both from the TMD hash) | no random source in the core | Low. No content is encrypted (type bit 0 clear), so the title key is not used. |
| Theme contents | none: bgm.bcstm before body_LZ.bin as in makerom's listing | Byte for byte the console-tested contents apart from the signature (checked for the three real zips against the installed pack, and in the tests against makerom's build of the fixtures). |
| TMD | none apart from the signature and the content hashes above | Header, title type, version, record IDs, indices, types and sizes are equal to makerom's (tested). |
| The zip and LZ11 checks are stricter than `theme_pack.py`'s | hostile input | A zip `theme_pack.py` packs can be refused: ZIP64, data before the archive, a member longer than declared, a body that does not decode to exactly its declared size (`theme_pack.py` checks only the first bytes). Both refuse a body that declares more than 0x150000 decoded bytes. None of the four real zips is refused (decoded sizes 0xa5760 to 0x1001e0). |

`tpack` writes a CIA only to feed `verify`; its certificate chain is copied from a CIA makerom made (this repo holds none). The console application imports the pieces through AM and needs no CIA. Its first install (1.0.0-beta.2) sends AM a TMD and, when the console has no ticket for the title, a ticket, both with the 0xFF signatures of the table's first row.

## Hostile input

Every length and offset of a zip, an SMDH and an LZ11 stream is checked before use: the end record and central directory against the file, local headers against the central directory, member data must end before the central directory, sizes against the limits before anything is decompressed (body 0x150000, BGM 0x337000, SMDH exactly 0x36C0), a deflate stream must produce exactly the declared size and CRC-32, the LZ11 stream must declare at most 0x150000 decoded bytes (the size of HOME's body buffer, `TP_E_TOO_BIG`) and decode to exactly that size without a back-reference before the start or past the end. An installed catalogue file is checked the same way: header, size, each entry's own index, UTF-8 text, icon size (`TP_E_CATALOGUE`). Allocations are bounded (largest 64 KiB, the end-record search). Refused: ZIP64, multi-disk archives, data before the archive, encryption, methods other than stored and deflate, a wanted name twice. If the source gives other bytes on the writing pass, the block hashes or the CRC-32 stop the write (`TP_E_CHANGED`, `TP_E_ZIP`).

A theme installer CIA is checked the same way before its zip is touched (`TP_E_CIA`, `TP_E_ENCRYPTED`): the CIA header (size 0x2020, type and version 0, content index 0 present), the sections at their 0x40 boundaries inside the file, the TMD's signature type and size, its first record being content 0, not encrypted and inside the content data; content 0 as an NCCH (magic, its size within the record, NoCrypto set, no NoRomFS, the RomFS inside it); the RomFS's IVFC header (magic, version, block size 2^6 to 2^20, master hash inside), level 3 at the first block boundary after the header and the master hash and inside the RomFS, its header (length 0x28) and the directory and file tables inside level 3; the root's file entries walked with a step limit (no loops), every name length and data range inside its table and level 3; `config.ini` at most 4 KiB, keys without regard to case, `location` only a plain file name at the root (letters, digits, space, `. _ - ( )`, not starting with a dot, no path), `destination` kept only if printable ASCII; the zip must exist where `location` says. With `verify` (the confirm screen and every download), the SHA-256 of content 0 must match its TMD record. Tested on CIAs makerom builds, on the user's example and on 20,000 mutated CIAs under the sanitizers.

## Memory

No content is held in memory. Pass 1 (in `tp_theme_open`) hashes the 4 KiB blocks of the theme's RomFS data while checking it; each content call streams the data again from the zip. Measured by the tests with the counting allocator of `tpack`: one content call needs 90,120 bytes (zlib's inflate state and 32 KiB window, 16 KiB input, output and sink buffers, the hash levels); an open theme keeps 32 bytes per 4 KiB of data, at most 38 KB for a theme at both limits; the peak of a whole run with the largest possible theme open was 126,984 bytes. Stack: the deepest chain of the core is about 2.7 KB on the 3DS (`-fstack-usage` with devkitARM), plus zlib's inflate. Cost: each theme's data is decompressed three times (open, measure, write) and hashed five times; not timed on a console. `tp_theme_drop_bgm` is the exception: it holds the whole body while it works, about four times the decoded body (the stored body, the decoded one, the new stream, a second decode to compare; 2.4 to 4.0 MB peak on six real bodies, `tpack nobgm`), and keeps the new stream (up to 0x150000 bytes) until `tp_theme_close`.

## Dependencies

- zlib for inflate and CRC-32, nothing else. It is in the macOS SDK (`zlib.h` 1.2.12) and in the devkitPro image as the portlib `3ds-zlib` 1.3.1-1, so it costs no vendored code, and it is the reference inflate that every zip reader leans on. zlib licence, compatible with GPL-3.0. Own inflate code would be several hundred lines to maintain and test against hostile streams; a single-file library would be vendored code doing the same job.
- SHA-256: 100 lines of own code (`core/sha256.c`, FIPS 180-4), constants computed from the primes, checked by the FIPS vectors and against Python's `hashlib`. zlib has none, CommonCrypto is Mac-only, mbedtls (3ds-mbedtls 2.28.8-1 in the image) is a large dependency for one function.
- The zip reader is own code (`core/zip.c`, 200 lines): it needs three members and strict bounds; minizip (in the image) would add a file-oriented API on top of the same zlib.
- The application adds (third party, all in the build, none of it Nintendo's): libctru 2.7.0-1, citro2d 1.7.0-1 and citro3d 1.7.1-2 (zlib licence) from the image; libcurl 8.4.0 (`3ds-curl` 8.4.0-1, curl licence, MIT-style) with mbedtls 2.28.8 (`3ds-mbedtls` 2.28.8-1, Apache-2.0) from the image's portlibs for downloads; quirc 1.2 (ISC) vendored in `app/vendor/quirc/` for QR codes: `lib/` of tag `v1.2` (commit `542848dd`) of [dlbeer/quirc](https://github.com/dlbeer/quirc), unchanged, from the tag's tarball (`gh api repos/dlbeer/quirc/tarball/v1.2`, sha256 `39295a364c933bc701a7c93acf86d35a297d253570ccf3c556c2dfe44ea485c3`), with its `LICENSE`. All of these ask that their copyright notice travels with copies; a release of the application should ship their notices next to it.
- Badges (0.9.3) add no library: the PNG reader (`core/badge_png.c`) is own code on zlib's inflate, a zip of PNG files goes through the core's zip reader, and the console's side is libctru's fs and APT.

The turning house (0.9.2): the application has no 3D code. `art.py` draws 60 pictures of the slab, 64 px square and 3 degrees apart (`LOGO_FRAMES`, `HERO_ICON`, `LOGO_STEP`; edge-on, face-on, edge-on: half a turn, and the slab looks the same from behind, so a whole turn shows them twice), each with its shadow, hairline, cut edge and the back face seen through the front, as one 512 x 512 RGBA8 sheet per glass style (8 by 8 cells, the last four empty). The three sheets are in the binary zlib-compressed in the GPU's tile order, and only the chosen one is unpacked into its texture (1 MiB) when the start screen is first drawn or the choice changes. The picture is chosen by the clock (`turn_picture` in `app/ui/turn.h`: one picture every 4 sixtieths of a second from the frame the screen opened, face-on first, 8 s a turn), so a late frame skips a picture and does not slow the turn. The pattern is one 64 x 64 texture per choice (since 0.9.3 per choice and colour scheme) (two tones at 78 %, `PATTERN_ALPHA`), drawn as one quad over the screen with the texture set to repeat (`C3D_TexSetWrap`, `GPU_REPEAT`; citro2d 1.7.0 passes a sub-texture's coordinates on as they are) and linear filtering, its coordinates moved by `turn_drift` 8 px a second (`PATTERN_DRIFT`) along the pattern's direction (`PATTERN_PLUS_DX` and so on in `uikit/include/ui_layout.h`), back where it was every 8 s. Every texel of a tile carries the tone of the shape nearest to it, also where it is see-through: the GPU's linear filter mixes the colours of neighbouring texels whatever their alpha, and the other tone there tinted a light shape's edge by up to 14 levels each time the drift passed half a pixel (found in review, by simulation). The pattern is not zoomed by a screen change, only faded.

Reading a folder and the installed designs, checking a theme, leaving out its music, deleting a design or a file, creating `/Themes`, downloading and, since 0.9.2, the install run as jobs on a worker thread (`threadCreate`, one priority step below the main thread, the same core) while the main thread goes on drawing; the worker draws nothing and reads no keys. It stays on the main thread's core, also on a New 3DS (libctru 2.7.0 `3ds/thread.h`, `svc.h`: core 2 only on a New 3DS and only with the exheader's permission, core 1 only after `APT_SetAppCpuTimeLimit`): on a core of its own it would run at the same moment as the main thread, which the jobs' plain variables and libctru's unlocked fs and am sessions are not built for, and on the same core it already gets all the time the main thread waits for the screen. If no thread can be made, the job runs on the main thread. While a job runs, the top screen goes on showing the screen it started from (0.9.2: no progress bar for a folder, the installed designs or a check; the download and the install keep their own screens), and so does the bottom screen, its cursor too, until the job has run for `LOADER_WAIT_MS` (150 ms); a job over within that wait shows nothing else, so a short load does not flash. ### What is installed, and the record

The application never trusts a file of its own alone. At start, and before the first write, it reads:

- AM's view (am:sys): `AMAPP_GetDLCTitleInfos` (installed, title version), `AMAPP_GetDLCContentInfoCount` and `AMAPP_ListDLCContentInfos` (index, content ID, size, installed and owned per content), and whether this title has a pending import (`AM_GetNumPendingTitles`, `AM_GetPendingTitleList`). The pack counts as not installed only when AM answers `0xD8A083FA` (the result Anemone3DS v3.0.1 ends its walk over the theme titles on, `source/themes.c` l.519); any other error is shown as an error with its code and nothing is written, so the application never creates the pack where one is installed. A pending import of the title refuses before that, also when AM does not know the title (a first install that was not cleaned up). Since 1.0.0-beta.2, and only when AM does not know the title, it also reads whether the console has a ticket for it, which decides whether the first install brings one: `AM_GetTicketCount`, then `AM_GetTicketList` in pieces of 256 title IDs (`this_title_ticket` in `console.c`; FBI's ticket list reads it in one call), searched for `0004008C00009809` only. A list that cannot be read, or gives fewer than the count, is an AM error and nothing is written. For an installed pack neither call is made, so its status calls are those of T3.
- The installed content 0 (catalogue), opened as Anemone3DS opens an installed theme DLC's contents (`dump_all_themes()` at tag v3.0.1): `FSUSER_OpenArchive(ARCHIVE_SAVEDATA_AND_CONTENT, {title low, title high, SD, 0})`, `FSUSER_OpenFile` with the binary path `{0, content index, 0, 0, 0}`, `romfsMountFromFile`. From it `ContentInfoArchive_EUR_en.bin` and `icons/<index>.icn`, read through `tp_installed_top` and `tp_installed_entry`.
- The record on the card, in `sdmc:/theme-pack/`:
  - `installed.tmd`: the TMD of the installed pack, raw bytes as in a CIA or a delta's `tmd.bin`. Needed because AM lists index, content ID and size but no hash, and a delta must carry the installed records byte for byte. It is used only if `tp_tmd_check` finds it equal to AM's list.
  - `installed.tmd.new`: the next TMD, written before the first AM write (read back and compared) and renamed over `installed.tmd` after AM's first commit. A failed install leaves it; it counts only if AM's list confirms it (a power cut between the commit and the rename, a commit AM carried out although it reported an error). When it is the only record that matches, the next install first renames it over `installed.tmd`, so staging the next TMD can never leave the card without a matching record.
  - `installed.mark` (and `installed.mark.new` while it is written): the highest content index ever handed out, as decimal text. Raised before the first AM write of every install, never lowered; the larger of the two files counts.

The first install (1.0.0-beta.2) writes the record as a delta does, so a pack the application created needs nothing from a computer. While AM does not know the title, record files of an earlier pack on the card (`installed.tmd`, `installed.tmd.new`) do not count and are not read against anything (`pack_assess` in `plan.c`); the first install stages its own TMD over `installed.tmd.new`, raises the mark and, after the first commit, renames the staged TMD over `installed.tmd`. If phase 1 committed and phase 2 failed, the pack is an installed one (version 0, the theme's record without its content) with a matching record, and the next install is a delta under a new index. If the record of a pack the application created is lost (the card's `theme-pack` folder emptied, another card), the application cannot make it again, because the console holds the TMD only encrypted. The way out: in FBI delete the title and the ticket of `0004008C00009809` (check the ID digit by digit; never System Settings, Data Management, see [`tools/theme-pack`, "Install (console)"](../tools/theme-pack/README.md#install-console)), then install the themes again here; the first of them creates the pack anew, and each gets the next index after the mark (if the mark is lost too, the paragraph below applies). A pack built on a computer can instead be seeded again from the Mac (next section). The problem screens for a pack whose record or catalogue is missing or does not match AM (`PACK_NO_STORE`, `PACK_STORE_BAD`, `PACK_STALE`, `PACK_NO_CATALOGUE`, `PACK_CATALOGUE_BAD` in `text_pack`) name both ways: for a pack built on a computer, reinstalling its CIA with FBI and copying its record from the Mac; for any pack, the application's own included, deleting the title and the ticket in FBI and installing the themes again here. The states themselves and what they allow are those of 1.0.0-beta.1.

The new theme's index is one above the largest of the mark, the catalogue's highest index and the TMD's (`tp_next_index`); for the first install, where AM knows no index, one above the mark alone (`plan_first` in `plan.c`): 1 on a fresh card, above the mark when an earlier pack left one, and the catalogue's top is that index (an index below it is listed as "(removed)"). So after the pack is reinstalled from a CIA with fewer themes (a recovery), the indices the console had handed out are still not given again. If the mark is lost as well (the card's `theme-pack` folder emptied), the next index comes from the catalogue and the TMD alone, and an index a later reinstall dropped may be handed out once more; layout slots and shuffle entries that still name it would then show the new theme. Seed the mark again from the Mac to avoid that.

A file whose theme name (as the catalogue cuts it, 63 bytes) and icon equal an installed theme's is refused as a duplicate; if that theme was deleted in HOME, it is added again under a new index.

### Seeding the record from the Mac

Only for a pack built on a computer with `tools/theme-pack` and installed with FBI; since 1.0.0-beta.2 a pack the application created has its record from the start (section above), and a console without a pack needs nothing of this. Someone still wants this path for a console that has such a pack already (as the console of T1 to T4 has) or for a pack built in one go from many themes (the application installs one theme at a time). Before the application's first install on that pack the card needs the record, because the console holds the TMD only encrypted: `installed.tmd` is the TMD that `theme_pack.py installed` records in `<data>/installed.json` (field `tmd`), and `installed.mark` the highest index the Mac's manifest handed out (its `next_index` minus one):

```sh
python3 -I -c 'import json, sys; sys.stdout.buffer.write(bytes.fromhex(json.load(open(sys.argv[1]))["tmd"]))' \
    "$THEME_PACK_DATA/installed.json" > installed.tmd
python3 -I -c 'import json, sys; print(json.load(open(sys.argv[1]))["next_index"] - 1)' \
    "$THEME_PACK_DATA/manifest.json" > installed.mark
cp -X installed.tmd installed.mark "/Volumes/<card>/theme-pack/"
```

After an FBI reinstall of the pack the record is stale and the application refuses until it is seeded again from that CIA's record (keep the mark: it only matters that it is not lower).

### The Mac follows the console (`theme_pack.py adopt`)

Once the application installs, the console is ahead of the Mac's `installed.json` and `manifest.json`. `tools/theme-pack/theme_pack.py adopt` brings them level: it takes the application's record copied off the card and the files the themes were installed from (zips, or theme installer CIAs, whose zip it takes out with ctrtool), finds each new content of the TMD by hash (the theme's content as makerom builds it, with the NCCH signature set to `0xFF`, which is what the core writes), copies each zip into `themes/` and records it in the manifest under the index the console gave it, and makes the TMD the new `installed.json`. It refuses, changing nothing, when the TMD's hash chain is broken, when it is not newer than the record, when a recorded content is not carried over unchanged (a reinstall in between: record that CIA first), when content 0 does not have the installer's ID, when a new content has no matching file, when a file matches no new content (also one that is recorded already), or when a zip's name is in the manifest already. Afterwards `theme_pack.py delta` builds on the console's state; it accepts kept contents that the installer built.

```sh
cp -X "/Volumes/<card>/theme-pack/installed.tmd" "$THEME_PACK_DATA/log/<date>-installed.tmd"
python3 -I theme_pack.py adopt --data "$THEME_PACK_DATA" --tmd "$THEME_PACK_DATA/log/<date>-installed.tmd" FILE...
```

A theme installed with "Ohne Musik installieren" matches no zip as it is (its content has no `bgm.bcstm` and a body with the music byte cleared). Give `adopt` a zip of that body and the theme's `info.smdh` instead; `tpack nobgm` writes the body exactly as the application makes it (the encoding is deterministic; host test `App.test_the_mac_adopts_an_install_without_music`):


### The AM sequence, and what it rests on

The sequence that passed on the console in T3 (`tools/theme-pack/import-test`, README section "Test application"; T3 on 2026-11-12: "AMNET_CommitImportTitles 00000000 ok", contents 1 to 3 KEPT, 4 NEW, content 0 NEW CATALOGUE, all installed and owned) and again in T4 with contents built by the core (2026-11-13, theme 5 added, listed and applied). Calls and result codes go to the log. Since 0.9.2 the sequence runs on the worker thread (`install_work`, screen 8) with the same calls in the same order and the same bytes as on the main thread before (host case 38).

| Step | Calls (libctru 2.7.0) |
| --- | --- |
| before any write | AM's view again and the record checked against it (`still_same` in `main.c`); the core measures content 0 (new ID `0x10000` + new version) and the theme, builds the new TMD (`tp_delta_tmd`) and checks it: title, version + 1, every installed record unchanged, the new theme last; a matching `installed.tmd.new` promoted; the next TMD staged; the mark raised |
| before any write, first install | AM's view again: the title still unknown, nothing pending, the ticket found or not as at the check (`still_same`); the core measures content 0 (ID 0) and the theme (ID = index), builds the whole TMD (`tp_tmd`, version 0) and reads it back (this title, version 0, the two records as measured), then the ticket (`tp_ticket`; ticket ID `0x0004000000000000` with the first six bytes of the TMD's SHA-256 in its low 48 bits, title key the digest's bytes 16 to 31, as `tpack pack` derives them, so the same theme at the same index gives the same bytes); the TMD staged; the mark raised (`first_pieces` in `install.c`) |
| ticket, am:net, first install | only when the console has no ticket for the title: `AMNET_InstallTicketBegin`, `FSFILE_Write`, `AMNET_InstallTicketFinish`, or `AMNET_InstallTicketAbort` after a failed write (`imp_ticket` in `console.c`) |
| phase 1, am:net | `AMNET_InstallTitleBegin(SD, 0004008C00009809, false)`, `AMNET_InstallTmdBegin`, `FSFILE_Write`, `AMNET_InstallTmdFinish(h, true)`, `AMNET_InstallContentBegin(0)`, `FSFILE_Write` in 128 KiB pieces as T3, `AMNET_InstallContentFinish`, `AMNET_InstallTitleFinish`, `AMNET_CommitImportTitles(SD, 1, false, &title)`; then the record renamed |
| phase 2, am:net | `AMNET_InstallTitleBegin`, `AMNET_CreateImportContentContexts(1, &index)`, `AMNET_InstallContentBegin(index)`, `FSFILE_Write`, `AMNET_InstallContentFinish`, `AMNET_InstallTitleFinish`, `AMNET_CommitImportTitles` |
| on a failure | `AMNET_InstallContentCancel`, `AMNET_InstallTmdAbort`, `AMNET_InstallTitleAbort` (whichever is open), then `AM_DeletePendingTitle(SD, 0004008C00009809)` if this title's import is pending or that is unknown |
| afterwards | AM's view read again and compared with the view before: kept, lost, new |

The first install (1.0.0-beta.2, `plan.first`: AM does not know the title) makes the delta's two commits on a title that is not there yet, with the ticket in front. That is FBI's sequence for a DLC title it installs anew (`source/fbi/action/installcdn.c` and `installtickets.c` of Steveice10/FBI at 5972e18, the commit before dd0ccff: the ticket, the title begin, the TMD, content 0, a commit, the title begin again, the import contexts for the other contents, a commit), so phase 1 on a missing title is FBI's main case. Left out of it on purpose: FBI's `AM_DeleteTicket` and `AM_DeleteTitle` (the title is not there, and the application never deletes a ticket) and `AM_QueryAvailableExternalTitleDatabase` (the delta path never called it, and a console that runs FBI has SD titles). The issuers of the core's TMD and ticket are the retail ones, so no certificate is imported. A ticket for the title that is on the console already (after a failed first install, or after the title alone was deleted) is kept and no ticket call is made: FBI never installs a ticket over one that is there, so what AM would do then is unknown. If AM then lists the new theme as installed but not owned, that ticket does not cover it, and the outcome says so with the way out: in FBI delete the title and the ticket of `0004008C00009809`, then install again (`judgement.not_owned`). A failure is cancelled as a delta's is; a ticket the install brought stays and is kept by the next try. What a console has shown of it: section "Unverified".

Safety: the title is `TP_TITLE_ID` in the core and refused otherwise, and the application names no other title (the console's ticket list is only read, to find this title's ticket); nothing deletes a title, a ticket or another title's pending import; the commit uses `temp = false`; everything the core can refuse is checked before the first AM write; every AM result is logged; a failure cancels only this title's own import. A theme from a CIA goes the same way: only the zip inside it is used, the CIA is never installed.

Every problem, refusal and empty state of the Designs and the Badges part has one form (FB-E, `ui_info_box`): the head with its sign in the top card, and on the bottom screen the explanation inside a box of the card's material, text only since C135 (from the box's inner left edge, the block centred in its height; a path or a code in a line of its own), never as bare text on the ground; a refusal that answers a press stays a note, with a sign above its text (warning, SD card). A sign stands only once on the pair of screens (FB-E2, `ui_sign_once` in `ui.h`): where the top screen shows the warning, in the card's head or as the footer's small glyph, the note under it goes without its own warning (the SD card's sign is the only other a note has, and the box has none since C135); the bottom screen's own controls (the corner button's folder) do not count.

Failures, and what the problem screen says (judged from AM's view afterwards, `install_judge`): nothing was written (a refusal before the first write); the import was cancelled and every installed theme is still installed; the catalogue was updated but the theme failed (HOME hides an entry whose content is not installed; trying again adds it under a new number); installed themes are lost; AM's view could not be read. A cancel after AM accepted the TMD may remove the installed themes (Azahar's AM deletes the title's content folder then; real AM is untested), so the screen reports what AM lists and names the way back: remove a pending import (FBI, Pending Titles, Delete Pending Title for `0004008C00009809`), then one of two ways, both of which the screen names: for a pack built on a computer, reinstall the pack CIA with FBI from `sdmc:/theme-pack/theme-pack.cia` and seed the record again; for any pack, also one the application created, delete the title and the ticket of `0004008C00009809` in FBI and install the themes again here (section "What is installed, and the record"). After a failed first install (1.0.0-beta.2) the words fit a console that had no theme of the pack: nothing was written (also when AM's view changed since the check), the import was cancelled and the pack was not created, or it was created with its catalogue and without the theme (trying again adds it under a new number), or whether it was created is unknown; never themes still installed or a pack CIA.

### Settings (0.9.2, 0.9.3)

`sdmc:/theme-pack/settings.txt`, read at start before the first frame (right after the log is opened, so the start screen's glass and pattern are right from the first frame on) and written whenever a choice changes (`app/source/settings.c`):

```
3DStockTheme settings 1
colour=white
music=somewhere-in-the-elevator.bcstm
sounds=on
glass=shard
pattern=houses
```

The first line names the format and its version; a file without exactly this line is not read. Then `colour=` (since 0.9.3: `white`, `yellow`, `sand`, `mint`, `sky`, `lilac`, `rose` or `night`), `music=` (a track's file name, or `off`), `sounds=` (`on` or `off`), `glass=` (`clear`, `shard` or `platin`) and `pattern=` (`plus`, `houses` or `bubbles`), in any order; lines this version does not know are skipped (also a `logo=` line, a name used before 0.9.2 was finished), a value it cannot use leaves that choice at its default, a file over 512 bytes is not read. A missing, cut, damaged or foreign file gives the defaults (since 0.9.3 Weiss, the first track of `tracks.h`, sounds on, Shard, the small houses; 0.9.2's were Clear and no scheme) and no error screen; a file of 0.9.2 (no `colour=` line) keeps every value it holds and gets Weiss, its `glass=` line keeping its style; so does a track the application is not built with. If the file cannot be written the choices hold until the application ends, and the log says so. The drawing asks `settings_scheme()` (0 to 7), `settings_logo()` (the glass style) and `settings_pattern()` (0 to 2 each), in the order of the file's words, which is the drawing layer's order (`ART_SCHEME_*` in the generated `ui_art.h`, `GLASS_*` and `PATTERN_*` in `ui.h`; `_Static_assert`s in `main.c` tie them); `tell_look()` passes all three to the drawing layer (`ui_look`) before every frame.

The menu music's tracks are one table in `uikit/include/tracks.h`: a line a track (symbol, file in `uikit/sound`, title, author, licence as taken, source page), the first one the default. The C table, the settings screen's rows, the sound data linked in (`uikit/source/sound_data.S`) and the test all come from it. Built in: "Somewhere in the Elevator" (22050 Hz) and "Urban Shop" (16000 Hz).

### Sound (0.9.2)

Sound goes through libctru's `ndsp` (2.7.0), which needs the DSP firmware dump on the card, `sdmc:/3ds/dspfirm.cdc` (libctru 2.7.0 `source/ndsp/ndsp.c` reads that path, or takes the copy the Homebrew Launcher hands over). The dump is made with Luma3DS (v13.5, `sysmodules/rosalina/source/menus/miscellaneous.c`): the Rosalina menu's entry "Dump DSP firmware" under "Miscellaneous options" writes `/3ds/dspfirm.cdc`, read out of the running HOME Menu; the menu opens with L + D-Pad Down + Select (`DEFAULT_MENU_COMBO` in `sysmodules/rosalina/include/menu.h`). Without it the application runs silent and the log says `sound: off, ndspInit answered D880A7FA (the DSP firmware is not on the card: sdmc:/3ds/dspfirm.cdc)` (D880A7FA is what `ndspInit` returns when it finds no firmware, computed from `3ds/result.h`; not seen on a console yet). With it: `sound: on, 6 of 6 interface sounds, music and working loop ready`, and before it `settings: read; menu music <file>, interface sounds on, logo N, pattern N` (or `settings: defaults (no file, or not one this reads); ...`; "logo" is the glass style's number). Every change on the settings screen writes `settings: menu music ..., interface sounds ..., logo N, pattern N` (with "; NOT saved ..." when the file could not be written).

- Loudness is the console's volume slider, which acts on everything the DSP puts out; the application reads no slider and sets only the kinds of sound against each other (`AUDIO_SFX_LEVEL` 0.80, `AUDIO_MENU_LEVEL` 0.35, `AUDIO_WORK_LEVEL` 0.60, `AUDIO_THEME_LEVEL` 0.80 in `uikit/include/audio.h`).
- Channels: 0 the menu music, 1 a previewed theme's music, 2 the working loop, 3 to 6 the interface sounds (four at once). The three kinds of music are BCSTM streams decoded a buffer at a time by `uikit/source/bcstm.c` on a thread of `audio.c`'s own, one priority step above the main thread, so they go on while the main thread is busy.
- `uikit/source/bcstm.c` reads a BCSTM held in memory (3dbrew "BCSTM"; written from that page, no code taken from elsewhere): PCM8, PCM16 and DSP-ADPCM, one or two channels, the loop from the file's loop points (the history at the loop start is the decoder's own, saved the first time it passes). A theme music without a loop plays once.
- The working loop (`uikit/source/work.c`, stepped by the audio thread after every sound frame, about 200 times a second): `main.c` says when work begins and ends (`audio_work(1)` in `job_start`, `audio_work(0)` in `job_ended()`, so every job has the pair, the deletes too; the install's end is in `run_install`, right before its done or error sound, so the loop goes on while the installing screen shows its last marks; the preview's reading has its own pair). Work that ends within `WORK_DELAY_MS` (= `LOADER_WAIT_MS`, 150 ms: the loop starts with the loader) changes nothing. After that the loop comes in over 120 ms (`WORK_LOOP_FADE_MS`) while the menu music fades out over 350 ms (`WORK_FADE_MS`) and pauses; when the work ends the loop fades out and the menu music comes back where it was. Work that follows work while the loop still sounds (a check right after a download) keeps it going. After an install the done or error sound closes the work: the loop fades out as it plays. The loop follows "Töne": with the sounds off there is no loop and the menu music plays on through the work. It is our own: `uikit/sound/make_working.py` writes it from plain tones (G major pentatonic, 108 quarter notes a minute, twelve soft mallet notes in a long-short-short rhythm and two beats of ringing out, 3.333 s), made after a reference the user gave for the kind of sound, with other notes and another rhythm; the reference is not in the repository.
- The files of `uikit/sound/` are linked into the application as they are (`uikit/source/sound_data.S`): seven WAVs (16-bit PCM, 32 kHz mono, 51 to 534 ms, 91 KB together), `working.bcstm` (42 KB) and the tracks of `tracks.h` (398 KB and 764 KB). `uikit/sound/CREDITS.md` has which file plays when, the sources with their licence lines, the working loop's notes and tempo and how to swap a file; `uikit/sound/wav2bcstm.py` (Python 3, standard library) makes a BCSTM from a WAV and turns one back into a WAV to listen to. The default track and `drop.wav` were chosen by ear, `back.wav` through an imitation of the console's speakers (`bong_001` itself, 232 Hz, could not be heard on the console; its octave is made from it, at -14 dBFS, by a generator that is not in the repository yet, see `CREDITS.md`), and `popup.wav` and `error.wav` were made louder for those speakers the same way (moved up by 4 and 14 semitones, at -14 dBFS, after the console played them very quietly and hardly at all); the other interface sounds and the working loop were chosen without listening and are a first set.

Which sound plays when (`sfx(...)` is called on the main thread only):

### Deleting a theme

"Design löschen" removes one content of `0004008C00009809` with `AMAPP_DeleteDLCContents(&index, 1, 0004008C00009809, SD)` through am:sys (libctru 2.7.0, IPC header `0x10040102`), the command the HOME Menu's own Delete sends: in the EUR 11.17 HOME code the delete task (`0x26dbc4`, count 1) reaches the AM wrapper at `0x15e978`, which writes the same header ([CODE] in `tech/3ds/themes.md`, "Managing single themes"). The plan is plain C (`app/source/deletion.c`, host tests in `host/test_app.c`):

- Only theme contents of the pack: any other title (`00009800` to `00009803` included), content 0 (the catalogue, without which HOME lists none of the pack's themes) and an index above 349 are refused before AM is asked, in the plan and again in the console's deleter. The index is the one the check found: the installed theme with the file's name and icon.
- The pack must have been read whole (also a full pack), AM's view must still match the record, no import of the pack may be pending, and AM must list the content as installed and owned.
- What the HOME Menu checks before its own Delete, read in its EUR 11.17 code (disassembled with capstone; addresses are HOME's): `0x241d04` compares the chosen theme with each of the ten shuffle entries in `SaveData.dat` from `0x13C0` (`0x221118`), with HOME's entry comparison `0x1fd4bc` (type 2 entries are equal when content index and variation are); the shuffle switch at `0x141B` is not consulted. A theme in that set gets the dialog `lau_theme_dlg_delete_rand` with only OK, then (`0x2c84c8` to `0x2c6188`) the normal question; on OK HOME empties all ten shuffle entries (`0x1d7230` writes the zero entry with `0x1fc158`) before it deletes. The theme in use (`0x1fd4bc` against the theme manager's current entry), or any delete while shuffle is on (`0x207fc4` reads `0x141B`), makes HOME first switch to no theme (the zero entry of `0x205520` through `0x23c11c`, state `0x23` waits for it), then delete; the dialog says which (`lau_theme_dlg_delete_1` for the theme in use, `_0` otherwise). So HOME refuses neither: it warns and fixes its own data. On the console (T2, 2026-11-12) HOME deleted the theme in use after a warning and switched to the default theme.
- This application never writes HOME's data, so it refuses both instead: it reads `SaveData.dat` (SD extdata `00000098` of the EUR HOME Menu, read only, opened as Anemone3DS v3.0.1 opens it in `source/fs.c`; 0x2DA0 bytes, 0x2CB0 on consoles that never grew it, 3dbrew "Home Menu") right before asking and again right before the AM call, and refuses a theme named by the entry in use (`0x13B8`) or by any of the ten shuffle entries, with what to do in the HOME Menu instead. When it cannot read that file it refuses as well.
- Nothing on the card changes except the log: AM keeps the content's TMD record (the TMD is not rewritten), so `installed.tmd` and `installed.mark` stay true and the theme reads as "deleted in HOME" afterwards; a later install keeps its record and gets a new index, as after HOME's own Delete. If the console stops during the call, the next start reads AM's list and finds the theme installed or deleted, both states it knows. The judgement afterwards (`deletion_judge`) reads AM's view again: deleted; not deleted (AM refused, or reported success and still lists it); other themes lost; unknown.

- Since 0.9.2 a delete runs on the worker while the main thread draws the loader; the main thread does not go back to its loop until the worker is done, so HOME, the lid, START and an order to close wait, and HOME and sleep are disallowed for the whole delete of a design (0.9.1: HOME only). The worker does everything the result needs: AM's view and HOME's data read again, the plan checked, the one AM call, AM's view afterwards, the judgement, then the pack read anew and with it the installed designs (asked on a design's screen) or the folder view the check screen came from (asked on a file's check screen); the main thread takes all of it over in one step. The AM calls and their order are those of 0.9.1. The log is strict while it runs (below, "The log").

"Datei löschen" removes exactly the chosen file (the theme closed first), on the worker as well; the theme stays installed.

### Without music

"Ohne Musik installieren" installs the theme's content without `bgm.bcstm` and with byte 0x5 of the decompressed body set to 0 (`tp_theme_drop_bgm` in `core/theme.c`, the LZ11 codec in `core/lz11.c`; it runs on the worker thread with "Musik wird weggelassen ..."). Why the byte too: HOME uses `bgm.bcstm` only when that byte is not 0 (3dbrew "Home Menu/Themes": "0 = disable usage of bgm.bcstm, non-zero = enable"; Anemone3DS v3.0.1 sets it to 1 when it installs music, `source/themes.c`, decompressing and compressing the body again), and a content with the byte 0 and no `bgm.bcstm` is the shape of the pack's theme 2 ("T1 Link Between Worlds"), which passed on the console in T1. A content with the byte set and no music file was never tried: HOME's apply path reads only `body_LZ.bin` from the content (`0x23b800`); where it reads `content:/bgm.bcstm` (a path table at `0x30acc8`, used by the theme cache task near `0x23d244`) was not traced to the end. In every real theme body at hand the byte is not a literal of the LZ11 stream but the start of a back-reference (5 bytes from 5 back), so it cannot be patched in place: the body is decoded, the byte cleared, the body encoded again (greedy, hash chains, the 0x1000 window), the new stream decoded once more and compared, and the content hashed again. On six real theme bodies the new stream was within 1 % of the original's size (8 to 23 ms on the Mac), and `ctrtool` and `theme_pack.py`'s own decoder found only byte 0x5 changed; the host tests do the same on the fixtures. A theme whose body already has the byte at 0 keeps its body; only its `bgm.bcstm` is left out (the check screen offers the second button only when the music would play).

"Schon installiert" does not tell the two apart: a theme is the same theme by its name and icon, with or without music, so installing the other variant means deleting the installed one first (then it gets a new index).

### Downloads

From the QR scan only; nothing about any site is built in, the code supplies the address (`app/source/download.c`, libcurl):

- http and https only, also after redirects (at most 5); the address must be one line without spaces.
- https is checked against a list of trusted certificates on the card, `sdmc:/theme-pack/cacert.pem`, and only against it: libcurl is always given that file (`CURLOPT_CAINFO`, and no certificate folder), so it never falls back to its built-in path (`sdmc:/config/ssl/cacert.pem` in the 3DS portlib). If the list is missing, an https address is refused before anything is sent, and an http address that redirects to https is not followed (redirects may then only go to http). The list is the one the curl project publishes (Mozilla's certificates, file `cacert.pem` with a `.sha256` beside it); fetch it on the Mac, check the sum, copy it to the card. It can be replaced without rebuilding the application.
- The application names itself in every request: `User-Agent: 3DStockTheme/<version> (Nintendo 3DS)`.
- At most 16 MiB (a theme's own data is at most 0x150000 + 0x337000 bytes; theme sites' zips also carry previews and a second copy of the music). Timeouts: 20 s to connect, and less than 100 bytes/s for 30 s ends the transfer.
- The file goes to `sdmc:/theme-pack/download.part`. It is kept only if its content is a theme zip or a theme installer CIA whose theme reads (`tp_theme_in` with the SHA-256 check, `tp_theme_peek`); then it is renamed into `sdmc:/Themes` under the `Content-Disposition` file name, else the address's last path part, else "theme", cut to letters, digits, space and `. _ - ( )`, with the extension of its kind and " (2)", " (3)" while the name is taken. On every failure and on a cancel the part file is removed, and the application removes a part file left by a power cut when it starts, so no partial file stays on the card.
- What it says when it fails: no web address in the code; https without the certificate list; no connection (curl's words); a certificate that does not check out; an HTTP status; too large; neither kind of theme file (for example a web page that asks for a browser check: sites may refuse automated clients, and the application does not try to get around that; download the theme on another device and copy it to `sdmc:/Themes`); a damaged theme; cancelled; the card could not be written.
- The network is started for each download and stopped after it (`socInit` with 1 MiB, `curl_global_init`); HOME and sleep are blocked while it runs, as during an install.
- For speed: the part file has a 256 KiB buffer of its own while it is written (`setvbuf`, freed after; without the memory it keeps the default one). The socket and curl keep their defaults: "G18" asked for a socket receive buffer of 256 KiB (`SO_RCVBUF`) and for 128 KiB pieces from curl (`CURLOPT_BUFFERSIZE`), and on the console the socket took the size (its line said "rcvbuf 8192 -> 262144") and then received nothing, not the response's first byte ("Operation too slow"), so both are gone (DL-2). With the console's default of 8192 bytes a download of 3.7 MB ran at 778 KB/s (its log, 2026-11-22), so nothing asks for more.
- Every download ends with one line in `install.log`, also when it failed or was cancelled: `download: <bytes> bytes in <ms> ms (<n> KB/s), first byte after <ms> ms, <n> pieces, largest <n>, <ms> ms in the file, rcvbuf <before> -> <after>, file buffer <bytes>`. The milliseconds after "in" run from the first body byte to the last (KB is 1000 bytes); "first byte after" is name lookup, connect, TLS and redirects (with no body byte the whole time); the pieces are what curl handed over; "in the file" is the time in `fwrite` and `fclose`; rcvbuf is the socket's receive buffer as `getsockopt` reads it when the socket is made and after the change (-1: not readable); file buffer 0: the part file had none of its own.

### Badges (0.9.3)

The Badges part adds badge sets to the HOME Menu's own badge collection ("die sollte man auch über QR sowie SD karte installieren können. am besten gleiches setup wie bei den themes, inkl. "Installierte Badges" oder so"). The collection is two files in HOME's extdata `000014d1` on the SD card, `BadgeData.dat` and `BadgeMngFile.dat`; the saved layouts are in extdata `0000165c`. What the bytes are is the badge core's (`core/badge.c`, `badge_png.c`, `badge_set.c`; plain C11 on zlib, buffers in and out, no file system and no console calls), which handles them the way the Mac tool `tools/badges/badge_sets.py` does: list the sets, append one set without changing anything that exists, remove the last set back to its earlier bytes, check that every placement points at a badge; for the same input the same bytes (host-tested against the tool). When which bytes go where is `app/source/badge_flow.c`'s; the only file with libctru calls is `app/source/badge_console.c` (HOME's two files in their extdata, opened read only for a listing and read and write for a write, never created; the main loop's turn with the system); the screens are `app/source/badges_ui.h`, included once by `main.c`.

- Sets: under `sdmc:/Badges` a set is a folder of PNG files, a zip of PNG files or one PNG (the badges' names and order as the Mac tool reads them). "Von SD installieren" lists the folders to open and the sets to choose, each with its icon and count, the first 500 entries of a folder (Y or the corner button goes one folder up, never above `/Badges`); the top screen is the carousel, as in the folder view. "QR-Code scannen" takes the Designs part's camera, link and download screens, their footer naming `/Badges`: a download is kept only when the core takes it as a set (a zip or a PNG), in `sdmc:/Badges` under a cleaned name no set there has yet, and opens the same check screen as a set from the card; on a failure or a cancel nothing partial stays.
- The check screen: "Installieren" with the count and the file, or why the set cannot be installed (a name the collection has already: "Ein Set mit diesem Namen ist schon im HOME-Menü.", no room, a file the core refuses).
- A write, an append or the removal of the last set, in this order (`badge_flow.h`): both of HOME's files are read whole and their sizes checked; the set and the manifest are read and the collection must take the set; both files as read are copied to `sdmc:/theme-pack/badge-backup/<number>/` with a `sha256.txt`, and the copies are read back and compared; the core changes the collection in memory, checks that only the set's areas change, and the result is read back as a collection; the new manifest and the set's undo record go to the card and are read back; `BadgeData.dat` is written in the set's areas only, then `BadgeMngFile.dat` whole in one call (a removal the other way round); the store is closed and opened again and both files are read back and compared with what was meant; if a write failed or the read-back differs, the backup is written back and read back ("Nicht geschrieben, Sicherung ist zurück"). Until the card's records are written nothing of HOME's files is touched. The newest three backups stay (`BADGE_BACKUPS_KEPT`). The work screen shows the set, the step ("Badges des HOME-Menüs werden gelesen", "Sicherung wird geschrieben", "Sicherung wird geprüft", "Wird vorbereitet", "Wird geschrieben", "Wird nachgelesen") and below it "Nicht ausschalten" and "SD-Karte nicht entfernen", on cards with the calm glass edge.
- IDs: the application's own manifest, `sdmc:/theme-pack/badge-manifest.txt` (ending in `end <sha256 of everything before>`; anything else counts as damaged and stops appends and removals), hands out set IDs from 0x7800 and badge IDs from 0x5800, the upper half of each of the core's ranges, so they never meet the Mac tool's, which counts upward from the lower halves; an ID present in the collection is passed over (a log line says so).
- Removal: "Installierte Badges" lists the collection's sets with icon and count (the carousel on top); one set's screen is built as the Designs part's one design (R15): the box of facts (the set's name, its badges) and one tile "Set entfernen" (the house of deleting). A set can be removed only when it is the last set of the collection, appended by this application, while its undo record is on the card (`sdmc:/theme-pack/badge-undo/<set ID>-<16 hex digits>.bin`, `.used` after the removal that used it) and none of its badges is placed in the HOME Menu; otherwise the tile opens an alert that says why ("Nur das zuletzt hinzugefügte Set kann entfernt werden.", "Dieses Set wurde nicht mit dieser Anwendung installiert.", and so on), the screen itself never does. When it can, a question comes first ("Set "<name>" entfernen?", "Abbrechen" and "Entfernen"). While a set is removed, Stock's top screen shows the loader (the ring of dots in the scheme's loader tone) under the title "Badges entfernen", with the step under way under it ("Sicherung wird geschrieben", ...); an install shows the filling vessel. HOME rewrites fields of its own in `BadgeMngFile.dat` once it is used (seen on the console on 2026-11-15: the placed counts, the case's view on the new set, the set record's + 0x28 of the last two sets, layout records it frees; `BadgeData.dat` never). The removal decides by the application's own bytes only (B2): every byte the append wrote in the set's areas must be what the undo record says it wrote; HOME's two fields inside them (each badge's placed count, which must be 0, and the set record's + 0x28) are not compared. Then only what takes the set out is written: the set's areas get their bytes from before the append (the counts, its used bits, its records, names and images), the case's view only if it names the set (it gets its value from before the append), and every other field keeps what HOME left in it; the log says whether the result is byte for byte the earlier file. The undo records of earlier builds are enough for this (their format is unchanged). All of it is decided before the backup: a refusal writes nothing, not even the backup. The refusals, under "Nichts wurde geändert": a byte the append wrote changed since (`BADGE_E_SET_CHANGED`: "Das HOME-Menü hat die Badge-Daten geändert, seit dieses Set installiert wurde, deshalb kann die Anwendung das Set so nicht zurücknehmen. Die Badge-Daten des HOME-Menüs sind wie vorher."), the set's badges not at the end ("Die Badges dieses Sets stehen nicht am Ende der Badge-Daten des HOME-Menüs. Nur das zuletzt hinzugefügte Set kann entfernt werden."), a badge placed, the undo record missing, unreadable or damaged ("Die Rücknahme-Datei des Sets auf der SD-Karte lässt sich nicht lesen oder ist beschädigt."), several records that fit ("Mehrere Rücknahme-Dateien auf der SD-Karte passen zu diesem Set, deshalb kann die Anwendung nicht sagen, welche stimmt."), HOME's data not laid out the way the application understands it.
- After a write, no restart (R13, decided by the console test of 2026-11-15): a set appended with the build that left the restart out was in HOME's badge case without a restart and still there after one (`install.log`: HOME read and rewrote its files with the set in them). That HOME takes a removal the same way is inferred from it, not seen. During the write HOME and sleep are not allowed, the log is strict and no input is read (`job_here`, as for an install), and `main.c`'s turn with the system (`console_main_loop` in `badge_console.c`, which is `aptMainLoop`) does not come round, so a POWER press (libctru 2.7.0 then asks for HOME whether HOME is allowed or not), a HOME press let through before the write or an order to close waits until the write is over. Then HOME and sleep are allowed again, whatever the outcome, and what waited is carried out. The Done screen after an install ("Installiert") and the problem screen lead back into the part with B, A or the tab "B Zurück", the Done screen as the Designs part's does after an install; a removal ends as a design's delete does (FB-E): back in "Installierte Badges", read again without the set (or its empty state), with the note that the set "wurde entfernt" (its badges gone from the HOME Menu, its file still on the SD card) and "Okay" over it; neither takes a touch that came down before it had been there `POPUP_GUARD_MS`. Before this the application held HOME and sleep off after a write and offered only a restart of the console (`APT_HardwareResetAsync`), on the guess that HOME keeps `BadgeMngFile.dat` in memory and would write its old copy back.
- The demonstration build (`DEMO=1`) pretends: its collection is a folder store in `sdmc:/theme-pack/demo-badges/` (both files zero-filled on first use, which the core reads as no sets), which also holds its manifest, undo records and backups, so HOME's files are never opened.
- Opening HOME's files (0.9.4): a listing (the part's footer, "Installierte Badges", the check screen) opens both files read only (`FS_OPEN_READ`), and a read-only handle is closed without a flush; a write opens them read and write as before, at its start, for the read-back and for the restore, in the order above. A failed open is told by its code's fields (`badge_open_kind` in `badge_flow.c`, the layout of libctru's `result.h`): description 230 of module FS (another process holds the file or the archive open) is "Die Badge-Daten sind gesperrt. Das HOME-Menü hält die Badge-Daten gerade offen. HOME drücken und zur Anwendung zurückkehren, oder 3DStockTheme als installierten Titel aus dem HOME-Menü starten. (Code ...)", summary 4 (not found) is "Keine Badge-Daten auf dieser Konsole" as before, any other code "Die Badge-Daten konnten nicht geöffnet werden"; the footer says "Die Badge-Daten sind gesperrt", "Keine Badge-Daten auf dieser Konsole" or "Die Badge-Daten sind nicht lesbar". A file of the wrong size keeps the not-found text. A write that meets the lock at its open has touched nothing: "Nichts wurde geändert" over the same text, no backup folder, no manifest or undo record changed. The log names the mode: `badges: HOME's badge files open (extdata 000014d1, read only)` or `(..., read and write)`, and a failed file open as `FSUSER_OpenFile (read only)` or `FSUSER_OpenFile (read and write)` with the code and the file. This answers the first console finding of 0.9.3: started as a `.3dsx` from the Homebrew Launcher, "Installierte Badges" showed "Keine Badge-Daten auf dieser Konsole. ... (Code C92044E6)" although the console has badges; C92044E6 is level status, summary cancelled, module FS, description 230 (in use), the case Anemone3DS answers with "Ext Data Locked" (HOME mounts `000014d1` and holds `BadgeData.dat` open read and write). Not known yet: which call failed in that run (`FSUSER_OpenArchive`, or `FSUSER_OpenFile` on which file; its `install.log` is not read) and whether a read-only open goes through while HOME holds the files. ### What the application leaves on the card

In `sdmc:/theme-pack/`: `installed.tmd` and `installed.mark` (the record), `installed.tmd.new` after a failed install (ignored while `installed.tmd` matches, replaced by the next install), and the log `install.log` with every AM result; when the log is larger than 256 KiB at start it becomes `install.log.old` (the previous `.old` is removed), so the two never hold much more than 512 KiB. In `sdmc:/Themes/`: the files it downloaded, each until the user deletes it (the question after an install, "Datei löschen", or by hand). A delete of a theme writes nothing but the log. Since 0.9.2 also `settings.txt` (section "Settings"), the empty `themes-folder.declined` when the user said no to creating `/Themes`, and `sdmc:/Themes` itself when the user said yes; the probe build adds `flicker-<n>-{bottom,top}-{target,fb}-{a,b}.raw` for the first four changes it finds. Since 0.9.3 the Badges part's `badge-manifest.txt`, `badge-undo/` and `badge-backup/<number>/` (the newest three; the demonstration build keeps all of it in `demo-badges/`), and in `sdmc:/Badges/` the sets it downloaded. Nothing else: no part file stays (see "Downloads"), no cache.

### Camera and lifecycle

The outer camera (`cam:u`, libctru 2.7.0, calls in the order of the camera example in the image) delivers 400x240 RGB565 frames; the main loop polls them without waiting, shows them on the top screen and gives each new frame to quirc in grey. The camera runs only on the scan screen: it stops when the screen is left, when a code with an address is found, when the application goes to the background or the console sleeps (APT hooks), and starts again when the scan screen comes back to the front.

### Limits

- One theme per install. At most 100 theme records in the catalogue (`TP_THEMES_MAX`, deleted themes count) and indices up to 349 (`TP_INDEX_MAX`); then the pack is full and the start screen says so.
- A theme deleted in HOME, or here, is added again under a new index, not under its old one.
- Deleting: one theme per delete, never the theme in use or one in the shuffle selection (HOME's own Delete does both); refused when HOME's `SaveData.dat` cannot be read. A full pack cannot be opened in the folder view, so its themes are deleted in HOME.
- One folder at a time, its first 500 entries. Theme folders (unzipped themes, as Anemone also reads them) are not supported: a folder is something to open.
- Downloads: http and https only, 16 MiB, https only with the certificate list on the card; a site that answers automated clients with a challenge page cannot be used from the console.
- Sound only with the DSP firmware dump on the card (`sdmc:/3ds/dspfirm.cdc`) or handed over by the Homebrew Launcher; without it the application is silent. The preview shows the wallpapers and the music only: not the moving squares, the folder, icon and cursor colours or the theme's own interface sounds.
- The settings screen shows four rows whole, more scroll by the stylus as a list's and by the D-pad (FIX-1); the top card holds six choices a row in one column (the eight schemes stand in two), the build refuses more.
- Badges: one set per write; only the last set of the collection can be removed, and only when this application appended it, its undo record is on the card and none of its badges is placed; a set named like one in the collection is refused; set IDs from 0x7800, badge IDs from 0x5800; at most 500 entries of a folder under `/Badges` are looked at.

### The log (0.9.2)

`sdmc:/theme-pack/install.log` (rotation as before, "What the application leaves on the card"). A line goes into a 16 KiB buffer and reaches the card when nothing moves on the screens (the main loop calls `console_log_flush` when no movement is being watched), not at once: a write to the card on the main thread right at a screen change cost frames. While the pack or the card is written (an install, a delete) the log is strict: every line is on the card before the next call is made. Closing the log writes what waits. After a crash the last lines of the moments before it can be missing unless an install or a delete was running. New lines:

- `speed-up: New 3DS (APT ...), ptm:sysm ... ok; a fixed piece of work took X ms before and Y ms after asking for 804 MHz and the L2 cache`, the second line of every start: Y is about a third of X when it took effect; "old 3DS", "FAILED" or two equal times mean it did not.
- `check times: T ms for N bytes: read A, CIA hash B, unzip C, LZ11 D, RomFS hash E, plan F, other G`, one per opened file.
- `motion: screen folder to check: first frame after 34 ms, 19 frames in 304 ms, slowest 17 ms`, one for every change of screen and every popup's opening and closing (`popup ... opened`, `popup ... closed`; "(cut short by the next)" when another movement began): "first frame after" is the time from the frame before to the first frame of the new screen (the work between the input and that frame is in it), the frames and the slowest gap are those of the 300 ms after it (`MOTION_MS`). At 60 frames a second a gap is 16 or 17 ms; 33 ms is a lost frame. After every install `motion: installing screen: N frames in M ms, slowest S ms`.
- `install step N at T ms` for each step of an install, as before; the `flicker probe` lines of the probe build (above).
- Since 0.9.3 the `settings:` lines name `colour <0 to 7>` first (the order of the file's words); the Badges part writes `== Append badge set "<name>" (<n> files)` or `== Remove the last badge set`, a `badges: ...` line for every stage (what was read, the backup written and read back, "written and read back as meant", a restore and its outcome, IDs passed over), the store's calls with their codes when one fails; a write's lines are strict, as an install's.
- `settings: ...` at start and at every change, `sound: on, ...` or `sound: off, ...` (section "Sound"), `preview of ...` for each preview, and the lines of the `/Themes` question (section "The folder /Themes").

## Open points

- The catalogue holds at most 100 entries (`TP_THEMES_MAX` in `core/tp.h`, checked in `check_catalogue` in `core/pack.c`, refused with `TP_E_ARG`), while indices run to 349 and are never reused. With 101 records in the installed TMD every delta fails, because each installed record needs a catalogue entry (`TP_E_GONE`) and the catalogue cannot take them; `theme_pack.py` has the same limit (`MAX_THEMES`). The 100 is taken from `theme_pack.py`, whose README sources it to HOME's theme list builder (0x23fdb0 in the EUR 11.17 HOME Menu code), which shows at most 100 themes in total, official ones included. No reason for it in HOME's catalogue reader is known here: as documented in `theme_pack.py`'s README, the reader takes entry *i* at 8 + 0xC8 × *i* and fails only if *i* exceeds the archive's count or the entry is disabled. The limit counts catalogue entries, which include themes HOME deleted, not the themes HOME lists; not changed.
- Two writers: after the application installs, run `theme_pack.py adopt` before `build` or `delta` on the Mac (section "The Mac follows the console"); until then the Mac's records are behind and `build` would hand an index out again. A `build` and FBI reinstall after adopting is consistent again. A pack the application created (1.0.0-beta.2) on a console that has no computer record leaves nothing to adopt: the console and its card are the only writer, and `adopt` matters only to someone who also builds on a computer. `adopt` cannot take such a pack up as it is: without `installed.json` it stops at its start (`load_installed` in `theme_pack.py`: record the pack first), and `installed` records only from a CIA or a delta folder with its `delta.json`, neither of which such a pack has. Whether the Mac can take up a pack the application created is not known; it is not built or tested.
- Bringing back a theme deleted in HOME under its old index (import only that content, no new TMD) would keep layout slots pointing at it; not built.
